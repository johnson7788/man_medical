## 安装与环境

### Q: `pip install torch` 卡住不动了

**现象**：命令跑十几分钟无输出，`venv` 目录体积不增长。

**原因**：PyPI / 国内镜像上的 `nvidia-*-cu13` 是 **0 字节占位包**，
解析某个大 wheel 时连接会挂住（实测文件零增长、CPU 几乎不动）。

**解决**：CUDA 版 torch 必须从官方源装。

```bash
uv pip install --index-url https://download.pytorch.org/whl/cu128 torch
# 其余包再走国内镜像
uv pip install --index-url https://pypi.tuna.tsinghua.edu.cn/simple \
  transformers peft trl datasets accelerate
```

### Q: 服务器没有 pip / git

```bash
apt-get install -y python3-pip git
# 或者用 uv（静态二进制，更快）
curl -LsSf https://astral.sh/uv/install.sh | sh
```

### Q: 下载基座模型很慢或中断

```bash
# 默认用 ModelScope（国内快）
python3 src/download_model.py --out models/MiMo-V2.6-Distill-Qwen-9B
# 换 HuggingFace
python3 src/download_model.py --source hf --out models/MiMo-V2.6-Distill-Qwen-9B
```

脚本支持断点续传，中断后重跑即可。完成后会**逐片校验完整性**。

> 校验提示：HuggingFace API 返回的文件大小是**十进制 MB**，
> 而 `ls -la` 显示的是二进制 MiB。换算比是 1.048576，
> 别把「5276.4 MB 期望 vs 5032.0 MiB 实际」误判成下载不全。

## 数据

### Q: 为什么没有原始 Excel？

原始表含院方真实数据，**不随仓库提供**（见 [`07_开源前必读.md`](07_开源前必读.md)）。
发布版从 `data/all_records.jsonl` 重跑，结果与发布数据一致：

```bash
python3 src/prepare_data.py                    # 发布模式
python3 src/prepare_data.py --from-xlsx 路径    # 你持有原始表时
```

### Q: `FileNotFoundError: 男科(2).xlsx`

同上。`load_raw()` 不再有默认路径 —— 这是刻意的，
避免发布版静默去找一个不存在的私有文件。

### Q: 剂量字段为什么全是 `1.000`？

原始数据 410,554 条剂量条目中 **99.7%** 是常量 `1.000`（HIS 导出问题），
无信息量，**已整体丢弃**。因此：

- 训练目标不含剂量
- 模型不生成剂量
- 部署时由 `dose_filler.py` 用药典标准量表填充

### Q: 为什么药味数和原始表对不上？

药名归一化会合并变体。原始 538 个药名 → 归一化后 **462 味**。
另外剂量后缀剥离曾有 bug（`酒黄精10g1.000` → `酒黄精10g` 被拆成两味），
影响 2,900 条记录，已修复并加 `assert_clean_herb_name` 硬断言。

## 训练

### Q: `AttributeError: 'Qwen3_5ForConditionalGeneration' object has no attribute 'print_trainable_parameters'`

`print_trainable_parameters()` 是 **PEFT** 的方法，只在 LoRA 套上之后才存在。
必须在 `SFTTrainer(...)` **构造之后**调用（SFTTrainer 内部才应用 `peft_config`）。
脚本已修正，并在之后加了可训练参数为 0 / >50% 的硬校验。

### Q: `TypeError: SFTConfig.__init__() got an unexpected keyword argument 'warmup_ratio'`

transformers 5.x **移除了 `warmup_ratio`**，替代是 `warmup_steps`。
脚本保留 `warmup_ratio` 作为本模块配置，在 `train()` 内按总步数换算。

### Q: `ImportError: You need to install bitsandbytes`

你用了 `paged_adamw_32bit`（QLoRA 的配套优化器）。
**bf16 LoRA 不需要 bitsandbytes**，用 `adamw_torch` 即可。
脚本按 `--quant` 自动选：`none` → `adamw_torch`，`4bit` → `paged_adamw_32bit`。

### Q: LoRA 训练完了但效果等于没训

**检查可训练参数占比。** 期望 **0.458%**（43.3M / 9.45B）。
如果是 0%，说明 `target_modules` 未命中任何层。

**根因**：基座是**混合注意力**架构，只有 8/32 层有 `q_proj` 等常见名字，
另外 24 层是 `in_proj_qkv`/`out_proj` 等。照抄 Qwen3 名单会**静默漏掉大半**。

```bash
python3 src/train_sft.py --model <path> --inspect   # 查看真实模块名
```

脚本默认用 `auto` 自动探测，一般无需手填。

### Q: `torch.OutOfMemoryError` 在 bs=16

实测 bs=16 需要约 95GB（96GB 卡几乎占满）。
**用 bs=8 + ga=2**（有效 batch 仍是 16），吞吐已足够（2.572 samples/s）。

### Q: 训练 3 个 epoch 效果反而更差

**正常，是过拟合。** v1 实测 eval_loss 0.4952（epoch1）→ 0.5052（epoch2）。
推荐 **2 epoch**，并依赖 `load_best_model_at_end` 自动回退。

### Q: `RuntimeError: Triton ... on Hopper GPUs produces incorrect results`

你装了 `flash-linear-attention`，而 torch 自带的 triton 版本在已知的错误区间
（≥3.4.0 且 <3.7.1，Hopper GPU）。**这会导致梯度错误。**

**解决**：升级 triton ≥ 3.7.1，或**卸载 fla 用参考实现**（正确但慢些）。

```bash
uv pip uninstall flash-linear-attention
```

> 另注：PyPI 上的 `flash-linear-attention` 与 `causal-conv1d` 是**冒牌包**
> （前者没有 `fla.ops`，后者只有 30KB 且无 `.cu` 文件）。真货在 GitHub。

### Q: 日志很久不更新，看不到训练进度

管道里的 `grep`/`sed` 会引入 **4KB 块缓冲**，非 tty 时输出被积压。
用无缓冲：

```bash
stdbuf -oL -eL python -u src/train_sft.py ... > train.log 2>&1
```

### Q: `pkill -f "xxx"` 把命令自己的会话杀掉了

`pkill -f` 的模式会匹配到**你自己这条命令行**（因为它含该字符串）。
症状是"命令没有任何输出、exit code 1"。

**解决**：用方括号技巧打断自匹配，或把清理与启动放在不同会话：

```bash
pkill -f "uv pip insta[l]l"      # 方括号版
# 或
ssh host 'pkill -f "src/app_model\.py"'   # 一个会话专门清理
ssh host 'setsid bash /data/run_app.sh > log 2>&1 < /dev/null &'  # 另一个会话启动
```

### Q: `pgrep -f train_sft.py` 明明没有进程却返回了 pid

同上，它匹配到了你当前这条 ssh 命令。用 `ps -eo cmd | grep "[t]rain_sft"`，
方括号同样是为了打断自匹配。

## 评测

### Q: 每 epoch 评测的分数看起来不对 / 输出只有两个空标题行

**检查 padding 方向。** decoder-only 生成**必须**用 left padding。

right padding 下短 prompt 的 pad 最多，首个 token 从 pad 位置预测 → 提前 EOS。
实测症状：17/64 条输出只有 `【中医诊断】\n【中药处方】\n`，**且全是短输入的初诊**。

```python
tok.padding_side = "left"    # 必须
```

`predict.py` 已加 `assert tok.padding_side == "left"`。

### Q: 模型的初诊分数到底是跟哪个基线比？

**必须同口径比。**

| 基线 | 总体 | 初诊 | 复诊 |
|---|---|---|---|
| Oracle（用真实诊断检索） | 0.208 | **0.254** | 0.182 |
| 复诊照抄 | — | — | **0.542** |

早期版本拿模型的初诊（0.218）去比 Oracle 的**总体**（0.208）,
得出"已超过"——**错了**。正确的初诊 Oracle 是 0.254。

### Q: 同一份模型，跑两次结果不一样？

可能原因（按概率排序）：

1. **批大小不同**。padding 长度不同 → matmul 归约顺序不同 → 个别样本 argmax 翻转。
   **比较两个模型时必须用相同 batch。**
2. 没设 `do_sample=False`。
3. 换了 triton / torch 版本（kernel 实现变了）。

### Q: `check_consistency.py` 报"过时说法仍存在"

先确认这些说法是否出现在**修订记录**小节里 —— 那里本就该如实记载修过什么。
脚本会排除 `### 16.6 修订记录` 与 `附录 C` 两节。

如果出现在正文，说明文档确实过时了，需要更新。

### Q: 我能只评测一部分样本吗？

可以，但注意 **ref 要同步过滤**，否则缺失预测会被按空输出计分：

```bash
# 分层抽样 1000 条
python3 src/predict.py --sample 1000 --out data/preds/sample.jsonl ...
# 然后把 ref 过滤到同一批 rid 再评测
```

`predict.py --sample` 已按初诊/复诊比例分层，固定种子可复现。

## 演示界面

### Q: 页面打不开

1. 确认服务在跑：`curl http://127.0.0.1:6010/`（服务器上）
2. 确认端口对外开放（防火墙）
3. 没开公网端口就用 SSH 隧道：
   ```bash
   ssh -N -L 7860:127.0.0.1:7860 <user>@<your-server>
   ```

### Q: 生成很慢

正常。每次都是**真实推理**（9.4B 模型，batch=1），约 19–48 秒/例。
模型加载约 10 秒（权重在 page cache 时）。

### Q: 演示输出和评测预测有个别差异

**预期现象。** 演示用 batch=1，评测用 batch=32，批大小会影响数值。

### Q: GPU 被别人占了，起不来服务

```bash
nvidia-smi --query-compute-apps=pid,process_name,used_memory --format=csv
```

9.4B 模型 bf16 需要约 19GB。若显存不足：
- 用 `--no-model` 只启动校验器页签（不需要 GPU）
- 或改用 4-bit 量化（`--quant 4bit`，需 bitsandbytes）
