> 报告日期：2026-10-08 ｜ 配套文档：`模型训练计划.md`（含 §16 状态台账）
> **全部数字均由可复现代码产出**，`./run_stage0.sh` 一键跑通 9 步。

## 0. 摘要

本项目要做的是：**根据患者四诊信息，辅助生成中医诊断与中药处方**。

经过完整的数据诊断与架构验证，我们得到三条决定项目走向的结论：

1. **处方不是证型决定的。** 即使把**真实**中医诊断喂给检索器（Oracle），处方 Jaccard 也只有 **0.208**。
   光靠证型标签查表无法解决 —— 模型必须从**现病史自由文本**里做个性化推断。

2. **处方本质是「治疗进程中的一次调整」。** 复诊占 **63.9%**，其最强预测因子是**上次开的方**
   （照抄即 **0.542**），而非中医诊断（复诊上仅 0.183）。当前"四诊→处方"的任务定义
   **丢掉了最强的输入特征**，已修正为 **T3+**（含既往处方），上界从 0.183 提到 **0.438**。

3. **两个不可回避的数据缺口。** 本方病历**几乎没有舌象与脉象**（舌 0.53% / 脉 0.74%），
   而医生是看着舌脉下的证型 —— 辨证存在**原理性**信息缺口；
   且**没有复诊疗效反馈**，模型只能模仿、无法解释。

**当前状态**：数据工程、评测体系、基线、外部知识库、约束校验器、训练脚本、演示界面
**均已交付**；模型训练**阻塞在 GPU 算力**（见 §8）。

## 2. 关键实测发现

### 2.1 基线全景（患者分组切分，train/test 零重叠）

| 类别 | 基线 | 处方 Jaccard |
|---|---|---|
| 下界 | 全局常量方 | 0.159 |
| **可实现** | **西医诊断检索** | **0.183** |
| Oracle | 证型+病名检索（**检索键=真实诊断**，现实中拿不到） | **0.208** |
| 端到端规则 | R0（先预测诊断→再用预测诊断检索） | **0.124** ⚠️ **低于常量方** |
| **治疗进程** | **复诊照抄上次方** | **0.542** |
| **新上界** | 复诊照抄 + 初诊 Oracle | **0.438** |

三条要点：

- **常量方就是 0.159。** 任何低于它的模型都是无效的。
- **两阶段管线是陷阱。** 诊断误差会传导放大，R0 = 0.124 反而**低于不做个性化的常量方**。
  这证明必须走**端到端联合生成**，不能拆成"先诊断后开方"。
- **「上次开的方」比整套中医诊断强 2.6 倍**（0.542 vs 0.208）。

### 2.2 处方是治疗进程的一次调整

| 证据 | 数值 |
|---|---|
| 同一输入却有多张处方的组，来自**同一患者复诊**的比例 | **97.8%** |
| 同一患者相邻两次就诊处方 Jaccard | **0.548**（隔次及更远 0.254，随机 0.075） |
| 复诊时完全不改方的比例 | 12.7% |
| 复诊调方幅度 | 平均删 5.2 味 / 加 5.3 味 |

**含义**：主诉/现病史常被医生逐字复制粘贴，记录**没有编码"这是第几次复诊、上次开了什么"**——
而这两件事在 HIS 系统里唾手可得。修正后的 **T3+** 把既往处方纳入输入，上界从 0.183 → **0.438**。

### 2.3 泄漏消融（同一套代码，只改切分方式）

按行随机切分时，test 的 **77.1%** 样本其患者已在 train 出现。

| 基线 | 患者分组（诚实） | 按行随机（泄漏） | 虚高 |
|---|---|---|---|
| 全局常量方 | 0.159 | 0.164 | +2.7% |
| 西医诊断检索 | 0.183 | 0.225 | **+22.8%** |
| Oracle（证型+病名） | 0.208 | 0.280 | **+34.7%** |
| D2 证型 micro-F1 | 0.368 | 0.480 | **+30.5%** |

> 常量方只虚高 +2.7%（它不依赖患者身份）—— 这个自检信号说明消融测的正是它该测的东西。

### 2.4 处方成因归因（各信息源的边际贡献）

逐药 macro AUC 累积消融：

| 信息层 | AUC | 边际增益 | 对应医生的依据 |
|---|---|---|---|
| 常量（性别/年龄） | 0.5432 | — | — |
| +西医诊断 | 0.6598 | **+0.1166** | **检查结果** |
| +证型/病名 | 0.7205 | +0.0607 | **中医指南**（辨证→治法） |
| +症状 | 0.7602 | +0.0397 | 四诊个体化 |
| +既往处方 | 0.8149 | +0.0548 | 经验 / 复诊调方 |
| +复诊间隔 | 0.8134 | −0.0015 | 无增益 |

⚠️ **AUC 与 Jaccard 给出不同结论，两个都要报**：检查结果对**排序**（某味药该不该用）
贡献最大（+0.117），但不足以**复现整张方子**（Jaccard 仅 0.183 vs 常量 0.159）。

**「中医指南」这一层其实是查表**：段级 `证型→治法` top1 占比 **85.7%**（多个证型 98–99%），
指南层面不产生额外自由度。

### 2.5 🔴 医师个人风格是真实存在的独立成分

在 4 个证型 × 25 个最集中的文书用语上做 16 组检验，**13 组显著（p<0.05）**，效应量极大：

| 文书标记 | 证型 | 两组方 top-15 Jaccard | 随机零假设中位 | p |
|---|---|---|---|---|
| 下肢水肿可自行消退 | 肾虚证 | **0.200** | 0.765 | 0.000 |
| 病史同前 | 肾虚证 | **0.154** | 0.765 | 0.000 |
| 可自行消退 | 肾虚证 | **0.154** | 0.765 | 0.000 |

**同一证型、同一患者画像，只因现病史里出现了某个文书模板用语，处方就系统性不同。**
这不是医学逻辑。**因数据无医生 ID，无法把"风格"与"患者亚型"彻底分开**——
这也污染了症状的贡献估计（+0.040 是**上界**）。

## 3. 技术架构：五步推理链

```
步骤1  症状/四诊            → 证型        数据监督（相同输入下 87.7% 一致，可学）
步骤2  证型                 → 治法        数据监督 + 确定性查表（段级 top1 85.7%）
步骤3  证型+症状+西医诊断    → 候选基础方   【检索】RAG，非生成
步骤4  候选基础方+症状       → 加减        数据监督（逐药增删）
步骤5  方中功效 ⊇ 治法       → 校验        外部中药字典，程序可校验
```

| 医生的思考 | 架构对应 | 监督/校验来源 | 状态 |
|---|---|---|---|
| 四诊合参 → 辨证 | 步骤1 | 数据标签 | ⚠️ 缺舌脉，有原理性上限 |
| 辨证 → 立法 | 步骤2 | 数据标签（确定性） | ✅ 已备 |
| 依法选方 | 步骤3 | 数据检索 | ⚠️ 天花板低（见下） |
| 随症加减 | 步骤4 | 数据 + 症状→药关联 | ✅ 关联已挖出 |
| 配伍禁忌 | 步骤5 | 外部中药字典 | ✅ **已交付校验器** |

### 3.1 ⚠️ 步骤3 的天花板（必须诚实面对）

只凭输入特征检索基础方：

| 场景 | 占比 | 基础方来源 | 强度 | 加减幅度 |
|---|---|---|---|---|
| **复诊** | 63.9% | **上次处方**（HIS 直接可取） | **0.542** | ±5 味 |
| **初诊** | 36.1% | 从输入检索 | **0.100**（top-1） | ±7.5 味 |

> **这个架构的价值集中在复诊；初诊存在原理性上限。想突破初诊上限只能补输入（舌脉），换算法无效。**

### 3.2 证型对处方的约束很弱（无偏估计）

| 条件 | 两两 Jaccard |
|---|---|
| 全部随机对 | 0.075 |
| 不同证型 | 0.074 |
| 同证型 | 0.116 |
| **同病名+证型** | **0.139** |

**即使病名+证型完全相同，两两处方 Jaccard 也只有 0.139** —— 这是 Oracle 上界只有 0.208 的根因。

## 4. 评测体系

### 4.1 指标

| 维度 | 指标 |
|---|---|
| 诊断 | 病名/证型/治法 micro-F1；证型 macro-F1（支持度 ≥20）；诊断集合完全一致率 |
| 处方 | **Jaccard（主指标）**；集合 P/R/F1；**关键药 Recall（top100）**；完全匹配率（仅观察） |
| 结构 | 非法药名率 / 重复药率 / 空方率 |
| 安全 | 毒性药样本率、寒热同用率（**预测 vs 参考并列**） |
| **子集** | **初诊/复诊**、处方重复/非重复、患者多次/单次、常规/异常药味数 |

**评测入口唯一**（`medlib.parse_assistant`），保证基线与模型分数可比。

### 4.2 Gate（实测校准）

| Gate | 必达 | 目标 | 依据 |
|---|---|---|---|
| G1 证型 micro-F1 | ≥ 0.55 | ≥ 0.65 | 基线 0.368 |
| G2 处方 Jaccard | **≥ 0.22** | ≥ 0.30 | **> Oracle 上界 0.208** |
| G2 关键药 Recall | ≥ 0.45 | ≥ 0.55 | > Oracle 0.403 |
| G3 非法药名率/重复药率/空方率 | ≤ 0.5% | 0% | 结构性硬指标 |
| G4 人工盲评（50 例） | ≥ 60% 可用 | ≥ 75% | 执业中医师 |
| G5 时间外推 Jaccard 相对下降 | ≤ 20% | ≤ 10% | 规则基线实测仅 0.4% |

**分口径目标**：复诊 ≥ 0.45（照抄即 0.542，低于此说明连照抄都不如）；
初诊 ≥ 0.22（须超过 Oracle 0.208，证明真的读了自由文本）。
**三个口径都要报**，只报总体会掩盖"初诊和以前一样难"。

> ⚠️ **不要用完全匹配率。** 初诊/整体口径下所有基线的完全匹配率都是 **0.00%**。

## 5. 已交付的工具链

### 5.1 约束校验器（`src/validate_rx.py`）—— 核心可上线件

```python
v = Validator()
v.validate_prescription(rx, tcm_dx, patient=None) -> dict
```

| 表现 | 数值 |
|---|---|
| 真实处方误报率（warn 及以上） | **5.62%**（ok 92.99% / note 1.39% / warn 5.57% / block 0.05%） |
| 安全类检出（幻觉药/十八反/妊娠/剂量上限） | **100.0%** |
| 缺失检测（删掉支撑治法的药） | **100.0%** |
| 治法判别（治法替换为无关） | ⚠️ **仅 7.9%** |

> 🔴 **能力边界**：它做的是**缺失检测**（方中有没有药支撑该治法），
> 不是**治法判别**（该治法选得对不对）。因此 **不可用作模型"治法"输出的奖励信号**。
> 原因：中医方剂功效多元（15 味药横跨多个功效类别），不相交的治法也能被"碰巧覆盖"。

**设计纪律**：

| 决策 | 依据 |
|---|---|
| block 只用于安全性 | 覆盖率硬拦会误杀医生处方（约 3% 是真实的标签/方药不一致） |
| 不做朴素寒热矛盾检查 | 真实处方寒热并用占 **17.3%**（交泰丸、乌梅丸即如此） |
| 毒性药提示不计入 verdict | 47% 真实处方含此类药材，计为 warn 会让 warn 级别失效 |
| 阈值全部外置 | 中医师改 `validator_config.json` 即可 |

### 5.2 治法→功效对齐表（`src/build_zhi_action_map.py`）

| 方案 | 平均覆盖率 | 完全覆盖 |
|---|---|---|
| 朴素 2-gram 字符串匹配 | 72.8% | — |
| **规则层（模式 × 真实词表）** | **96.0%** | 92.3% |
| 规则 + 数据共现 | **96.9%** | **93.4%** |

> ⚠️ **踩过的坑**：第一版按中医教材术语手写功效名（`补肾阳`/`滋阴`/`补血养心`），
> 但本草典用的是另一套词（`补肾助阳`/`养阴润燥`/`养血补心`）——
> **手写的 171 个功效名里 27% 在字典中不存在**，静默失败，覆盖率卡在 72.8%。
> 改成「正则模式 × 真实词表」后升到 96.0%。

### 5.3 剂量填充层（`src/dose_filler.py`）

模型**不生成剂量**（原始数据无真剂量，编造 = 临床风险）。剂量由标准量表填充：

- 可填充剂量的用量占比 **94.44%**
- 有毒/需特殊处理药材取**区间下限**（宁少勿多）
- 恒返回区间与原文说明（含炮制差异，机器无法替医生决定）
- 字典缺失显式标注「待人工填写」，不留空、不猜
- 强制附加免责声明

### 5.4 约束解码（`src/constrained_decode.py`）

| 约束 | 手段 |
|---|---|
| 药名 ∈ 462 白名单 | **trie 逐 token 引导**（正确处理多 token 药名）+ vLLM guided_json / guided_regex |
| 十八反/十九畏 | **集合级**约束，语法表达不了 → 「生成→校验→剔除违规药→重生成」有界修复 |
| 功效覆盖治法 | **不做硬约束**（判别力仅 7.9%），仅作可读提示 |

离线自检全通过（无需 torch/vLLM）：462 味全部沿 trie 可达、3000 次受约束生成零越界、
guided_regex 462/462 命中且拒绝白名单外药名、十八反修复循环生效（attempts=2）。

### 5.5 训练脚本（`src/train_sft.py`）

相对常见 SFT 参考实现的 7 处改动（含计划要求的 5 处 + 本项目特有 2 处）：
lr 2e-4→**1e-4**、**加 val 与早停**、max_length 2048→**1024**、
**清理注释掉的 `get_peft_model` 死代码**、显式 **packing=False**、
**初诊/复诊分开评测**、**接入约束校验器监控**。

`--dry-run` 实测（无需 GPU）：

- train/val 与 `ref_*` 条数一致（各 21,484 / 2,675）
- val 同时含初诊 996 / 复诊 1,679（62.8%）→ 分开评测可行
- 序列长度 p99=360、max=531 → **max_length 1024 充裕，可收窄到 512**
- 步数 ≈ 2,685/epoch，3 epoch 共 **8,055 步**

## 6. 安全与合规

### 6.1 数据合规
- 真实 11 位病历号 → **哈希脱敏**（`medlib.hash_pid`）
- 自由文本 PHI（身份证/手机/住址/姓名）**尚未脱敏** → 需合规审批
- 本草典为 **CC BY-SA 4.0**：产出若使用其内容需同许可共享并署名
- 其余源标注学术/研究用途，**不得商用**

### 6.2 临床安全
- **剂量一律不由模型生成**（§5.3）
- 十八反十九畏 + 妊娠禁忌 + 毒性药上限 + 幻觉药 → **约束解码期硬拦 + 后置校验**双保险
- 毒性药安全提示覆盖 **100%**（13,404 次毒性药使用全部有警示）
- 输出强制携带免责声明；产品定位 **医师辅助/教学**，不是自动开方
- 上线前 **G4 人工盲评不可省**，评审人须为执业中医师

### 6.3 待复核项
- 十八反命中 **50 条（0.186%）**，主要为 `丁香+郁金`（十九畏条目，中医界对其绝对性有争议）
  → 已在配置中**降级为 warn**，需中医师确认是否拦截
- `治法→功效` 映射表中 **362 条 data 来源条目未经医理确认**

## 7. 不建议的做法（有实测依据）

| ❌ 做法 | 为什么 |
|---|---|
| 拆成「先诊断→再开方」两阶段 | 实测 R0 = 0.124，**低于常量方 0.159** |
| 用完全匹配率评估 | 诚实口径下所有基线均为 **0.00%** |
| 按行随机切分 | 指标虚高 **+22.8%~+34.7%** |
| 让模型生成剂量 | 数据里没有真剂量，会编造 |
| 用强模型凭空生成"辨证思路"再 SFT | 事后合理化，且推理链无 ground truth 无法评估 |
| 朴素的"寒热同用即矛盾"检查 | 真实处方寒热并用占 **17.3%**，会大面积误杀 |
| 把覆盖率校验当治法判别器/奖励信号 | 判别力仅 **7.9%** |

## 9. 一句话结论

> 这份数据支持的是**「处方推荐 + 可审核的相对调整说明」**，**不支持「处方解释」**。
>
> 想让模型"知道为什么"，第一步不是加思维链，而是：
> ① 补输入（**既往处方**，已做；**舌脉**，需院方）；
> ② 补知识库（**药典功效**，已做；**方剂方解**，部分做）；
> ③ 补**疗效反馈**（需院方）—— 在拿到疗效数据之前，
> 任何"模型能解释处方理由"的说法都不成立。
